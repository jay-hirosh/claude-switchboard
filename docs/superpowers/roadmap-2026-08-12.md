## Phase 1 — Live session engine (F1 → F2 → F3) — ✅ Shipped

The shared core is a **live session registry** (`src-tauri/src/live_sessions.rs`): a backend module that correlates the file watcher's per-touch signal with actively-growing JSONL transcripts to answer "which sessions are running right now, and what have they consumed so far this session." Built once for F1; F2 and F3 turned out to be thin rules on top, exactly as planned.

### F1. "Now running" row — ✅ Shipped
Spec: `specs/2026-08-12-live-sessions-f1-design.md`. Plan: `plans/2026-08-12-live-sessions-f1.md`.
Popover section showing each live session: project name, model, cost, elapsed time — capped at 3 rows + "N more". Liveness resolved to Live (touched within 120s) → Cooling (120–300s) → removed (300s+), started strictly from watcher-driven ingest so the startup backfill never populates it. Final review caught and fixed two real bugs before merge: the popover had no content-height measurement at all and would clip its own footer the instant a session went live, and the subagent-transcript folding logic used a forward-slash string search that silently breaks on Windows.

### F2. Session-finished notifications — ✅ Shipped
Spec: `specs/2026-08-12-session-finished-f2-design.md`. Plan: `plans/2026-08-12-session-finished-f2.md`.
Native notification when a session that ran ≥10 minutes goes quiet for good (F1's Cooling→removed transition). Settings toggle, default on. Final review caught and fixed a dedup bug that would have permanently blocked a legitimate second notification for a session resumed after departing.

### F3. Context-window warning — ✅ Shipped
Spec: `specs/2026-08-12-context-warning-f3-design.md`. Plan: `plans/2026-08-12-context-warning-f3.md`.
Notification plus an amber popover chip when a live session's context crosses 80% of its window (hysteresis re-arms below 70%). Final review caught and fixed a Critical bug: the original 200K fallback for unrecognized models was factually wrong for this app's own shipped provider presets — GLM's real window is 1M (so it false-alarmed at 16% of the real window) and DeepSeek's real window is 131K (so the warning could never fire before real compaction). Fixed to skip the warning entirely rather than guess, matching the frontend's existing null-safe philosophy.

**Known, deliberately-parked limitation carried across all three:** liveness/"still working" detection is keyed to new *costed* transcript events, not every raw write — a session mid-way through a long tool call (a slow build, a long test suite) writes nothing for the duration, so it can depart and re-register with a fresh notification cycle. Surfaced independently in F1's, F2's, and F3's own final reviews; deserves one real design pass rather than a third patch. Not fixed on any of these three branches.

## Phase 2 — Guidance from history (F4, F5 → F6) — ✅ Shipped

### F4. Model routing advisor — ✅ Shipped (S)
Spec/design discussed inline during brainstorming (no separate design doc — bounded-path feature). One-line hint in the popover when per-model 7D buckets diverge sharply: *"Opus 7D at 82%, Sonnet at 31% — consider switching."* Fires when the busier bucket clears the warn threshold (75% default) and the gap between models is ≥25pp; dismiss is scoped to the current 7-day window (keyed off `resets_at`), so the hint reappears if the gap recurs next week. Pure frontend, `src/lib/modelRoutingHint.ts`.

### F5. Limit-hit analytics — ✅ Shipped (M)
Spec: `specs/2026-08-13-limit-hit-analytics-f5-design.md`. Plan: `plans/2026-08-13-limit-hit-analytics-f5.md`.
**Correction found during brainstorming:** the roadmap's premise above was wrong — `api_snapshots` is pruned to 50 rows per account (~4 hours of history at the default poll interval), not "full history." It exists purely for cold-start rehydration. Built a new dedicated `window_peaks` table instead, updated incrementally on every poll (one row per finished 5H/7D window, keyed by `(account_id, bucket, resets_at)`). New "Limit hits" tab: per-account hit counts, hour-of-day distribution, top-projects attribution. Final whole-branch review caught and fixed a real double-counting bug (a 5H hit's window always nests inside its enclosing 7D hit's window, so shared events were summed twice) and cross-account attribution bleed (`session_events` has no account_id, so per-account project lists were global, not account-scoped — fixed via honest UI labeling + a documented spec limitation, not a data-layer rewrite). Also fixed, as a useful side effect: the pre-existing `theme.test.ts` collection failure (Node 22+'s built-in `localStorage` was shadowing jsdom's working one under the test runner) — see the Remaining follow-ups list below, now resolved.

### F6. Smart warm-up suggestions — ✅ Shipped (S)
Suggests a warm-up anchor time from observed activity: *"You usually start around 08:40 — Apply?"* Median first-event-of-day local time across the trailing 90 days, gated behind a 10-active-day floor. No weekday/weekend split (single suggestion — simpler chip, and warm-up only has one anchor slot to fill anyway). Surfaces as a dismissible-by-nature chip in `ScheduleSelector` (disappears once the anchor matches, no persistent dismiss state needed); never auto-applies.

## Phase 3 — Outward surfaces (F7 shipped; F8, F9 remain)

### F8. Finish the macOS widget (M — resume existing work first)
Tasks 4–6 of the existing WidgetKit plan, on the unmerged `widget` branch (`native/macos/SwitchboardWidgetHost`). **Do early in Phase 3 or in parallel with Phase 2** — it's half-built, and unfinished branches rot as `main` moves. First step of its plan: rebase `widget` onto `main` and re-validate tasks 1–3.

### F9. Reset timeline view (M)
Horizontal timeline: every account's 5H/7D reset moments plus scheduled warm-up fires on one axis. Answers "account B frees up at 4pm, C at 6pm."
- Pure frontend over existing data (`resets_at` per bucket per account, warm-up schedules via `get_warmup_state`). Natural pairing with the best-account indicator — likely lives in the expanded report near the accounts sidebar.
- **Design questions:** time span (next 24h?), whether 7D resets (days out) share the axis or get a separate lane.

### F7. Statusline installer — ✅ Shipped (M–L — most external-surface risk)
Spec: `specs/2026-08-13-statusline-installer-f7-design.md`. Plan: `plans/2026-08-13-statusline-installer-f7.md`.
One-click install of a `switchboard statusline` command into Claude Code's `statusLine` config, showing 5H% in the terminal prompt. Chose the shared-snapshot + CLI-reader architecture over a standalone CLI with its own DB/account-detection: the poll loop now also *writes* the previously-read-only `~/.claude/statusline-usage.json` (built originally to consume a third-party daemon's output for rate-limit-budget sharing — this is its first writer), and the CLI subcommand (`cli.rs`'s first true subcommand — it had zero subcommand parsing before this) just reads that file back. Reuses the Providers feature's guarded-write machinery as planned, though that machinery needed widening from private to `pub(crate)` first, not the "already shared" the roadmap assumed. Final review confirmed, via independent state-space analysis, that no path silently overwrites a user's hand-written `statusLine` — the core risk this feature was flagged for. It also caught and fixed a real cross-task bug: the shared-snapshot writer originally re-stamped its own re-adopted (unchanged) data as fresh on every write, which silently defeated manual "force refresh" for the active account; and a second one where the statusline's fixed 10-minute freshness window was shorter than the app's own configurable polling interval ceiling (30 minutes), so anyone polling slower than 10 minutes saw a permanently-stale "not running" placeholder. **Known limitation, unverified:** this session's environment is macOS-only, so the Windows behavior of the release binary's `windows_subsystem = "windows"` setting when Claude Code invokes the CLI subcommand has not been tested — needs manual verification on Windows before this is considered fully production-ready there.

## Phase 4 — V3 analytics batch — ✅ Shipped (7 of 7)

Seven new analytics features, scoped in a 2026-08-13 brainstorming session as a follow-on to F5 (limit-hit analytics), all shipped 2026-08-14. None overlap the 8 shipped report tabs (Cache, Heatmap, LimitHits, Models, Repo, Sessions, Trends, Providers) or PAYG's existing $ burn-rate — each fills a gap explicitly identified against those. Chart-treatment mockups (radial gauge, ranked bars, sparkline+delta strip, pacing bar) were reviewed and approved via the brainstorming visual companion before this batch was locked in.

Two features shrank during implementation once the actual code was checked against the roadmap's assumptions — the same pattern F5 hit with `api_snapshots` back in Phase 2: Model cost-efficiency turned out to need zero backend change (data already fetched), and Session leaderboard turned out to already half-exist (the Sessions tab already sorted by cost). Worth remembering for the next batch: check what's already there before sizing a new feature.

**Shared infrastructure — corrected during Model cost-efficiency's implementation:** the "rollup query layer" below was originally scoped as new shared infra, but the actual backend pattern (`get_session_history(days)` → `db.events_between()`, already an arbitrary-range SQL query) turned out to already cover it — every report command just groups the result differently in-memory (see `get_model_breakdown`, `get_daily_trends` in `commands.rs`). The only genuinely new shared piece is a small day/week/month bucketing helper, needed by period-over-period, monthly pacing, and anomaly flagging — build it when the first of those three is picked up, not speculatively now.
