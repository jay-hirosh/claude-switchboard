## Phase 1 — Live session engine (F1 → F2 → F3)

The shared core is a **live session registry**: a backend module that correlates running Claude Code processes with actively-growing JSONL transcripts to answer "which sessions are running right now, and what have they consumed so far this session." Built once for F1; F2 and F3 are thin rules on top.

### F1. "Now running" row (M — largest single piece; builds the registry)
Popover section showing each live session: project name, model, cost/tokens ticking, elapsed time. *"fix-auth-bug · Opus · $1.84 · 12m"*.
- **Backend:** new `live_sessions` module — a session is "live" when its JSONL file received events within the last N seconds AND a matching process exists. Aggregate per-session running totals from watcher events (the watcher already parses every event; add an in-memory per-session accumulator, no new DB table). New IPC command `get_live_sessions` + a `live_sessions_changed` event.
- **Frontend:** collapsible section in `CompactPopover.tsx` between the bucket bars and footer; hidden when no sessions are live. Reuse `SessionRow`'s model-badge conventions.
- **Design questions for its spec:** liveness window (30s? 60s?), whether subagent activity rolls into the parent row (mirror the Sessions tab's grouping), max rows before overflow.

### F2. Agent-finished notifications (S — registry + one notifier rule)
Notify when a long-running session goes quiet: *"claude-switchboard session finished — $2.10, 34m."*
- A session that was live ≥ X minutes transitioning to not-live fires one notification. Opt-in toggle in Settings → Notifications; per-session dedup via the existing `notification_state` pattern.
- **Design questions:** minimum-duration threshold to avoid noise from quick sessions; whether "finished" needs the process gone or just the transcript quiet.

### F3. Context-window warning (S–M)
Alert when a live session's context approaches compaction.
- Context math must move to (or be duplicated in) Rust: port `contextWindow.ts`'s `NATIVE_1M_MODELS` logic — keep one source of truth by generating or testing the two lists against each other. Current context size comes from the latest event's cumulative input tokens per session, already parsed by the watcher.
- One threshold (e.g. 80% of window), once per session per threshold, same dedup machinery as F2.
- **Design questions:** threshold value and whether it's configurable; in-popover indicator on the F1 row (probably yes — a small % chip) in addition to the notification.

## Phase 2 — Guidance from history (F4, F5 → F6)

### F4. Model routing advisor (S)
One-line hint in the popover when per-model 7D buckets diverge sharply: *"Opus 7D at 82%, Sonnet at 31% — consider `/model sonnet`."*
- Pure frontend: `seven_day_opus` / `seven_day_sonnet` are already in every `CachedUsage`. A pure function (like `bestAccount.ts`) decides when the gap is actionable; renders as a dismissible hint row.
- Only renders on plans that report the per-model split (Pro/Team-Pro return null — same guard as the existing per-model bars).
- **Design questions:** gap threshold; dismiss-until-reset vs dismiss-forever.

### F5. Limit-hit analytics (M)
Report tab (or Trends section) answering "when do I actually run out?": count of times each bucket hit ≥95–100%, time-of-day distribution, which projects consumed the window beforehand.
- **Backend:** mine `api_snapshots` (full payload history already stored per account) for utilization peaks per window cycle; join window-start times against `session_events` to attribute consumption. New read-only IPC command; no schema change.
- **Design questions:** where it lives (new tab vs Trends section); how far back (30/90 days); per-account or active-account-only.

### F6. Smart warm-up suggestions (S — after F5)
Suggest warm-up anchor times from observed behavior: *"You usually start around 08:40 — anchor warm-up at 08:30?"*
- Reuses F5's history-mining: median first-event-of-day time from `session_events` (already timestamped). Surfaces as a suggestion chip in the warm-up `ScheduleSelector`, never auto-applies — warm-up stays strictly opt-in.
- **Design questions:** minimum history before suggesting (e.g. 10 active days); weekday/weekend split.

## Phase 3 — Outward surfaces (F7, F8, F9 — independent of each other)

### F8. Finish the macOS widget (M — resume existing work first)
Tasks 4–6 of the existing WidgetKit plan, on the unmerged `widget` branch (`native/macos/SwitchboardWidgetHost`). **Do early in Phase 3 or in parallel with Phase 2** — it's half-built, and unfinished branches rot as `main` moves. First step of its plan: rebase `widget` onto `main` and re-validate tasks 1–3.

### F9. Reset timeline view (M)
Horizontal timeline: every account's 5H/7D reset moments plus scheduled warm-up fires on one axis. Answers "account B frees up at 4pm, C at 6pm."
- Pure frontend over existing data (`resets_at` per bucket per account, warm-up schedules via `get_warmup_state`). Natural pairing with the best-account indicator — likely lives in the expanded report near the accounts sidebar.
- **Design questions:** time span (next 24h?), whether 7D resets (days out) share the axis or get a separate lane.

### F7. Statusline installer (M–L — most external-surface risk)
One-click install of a Switchboard-provided statusline command for Claude Code, showing 5H% in the terminal prompt. Inverse of the existing snapshot *reading* — Switchboard becomes the writer.
- Writes a `statusLine` entry to `~/.claude/settings.json` — must reuse the Providers feature's guarded-write machinery (backup + undo manifest + confirmation), same as the global-default-provider flow.
- **Design questions:** what the statusline binary/script actually is (shell script reading the shared snapshot vs a `switchboard statusline` CLI subcommand — the CLI already exists as `cli.rs`); coexistence with a user's existing statusline. Riskiest of the nine to get right; deliberately last.
